# Разворачивание YOOMP на Selectel — боевой контур в РФ

> Стенд для демо на общем сервере Hetzner описан отдельно:
> [`hetzner/README.md`](hetzner/README.md). Он не заменяет этот контур.

Контур целиком в РФ. Это не предпочтение и не осторожность: фото чужих
машин с читаемыми госномерами плюс имена и телефоны клиентов — персональные
данные граждан РФ, а ст. 18 ч. 5 152-ФЗ требует, чтобы их запись,
систематизация и хранение шли в базах на территории РФ. Юрлицо проекта
зарегистрировано как оператор ПД, и весь контур обязан этому соответствовать.

Отсюда два следствия, которые не обсуждаются:

- **Vercel и Supabase Cloud исключены.** Оба хранят данные вне РФ. Хостинг
  приложения на Vercel означал бы, что фото и телефоны клиентов проходят
  через чужой контур за границей.
- **Внешних CDN в продукте нет.** Шрифты Onest, рендеры и скрипты отдаются
  со своего контура. В `nginx/security-headers.inc` это закреплено политикой
  CSP без единого внешнего источника: появится в разметке чужой домен —
  страница сломается на проверке, а не тихо уведёт трафик клиентов наружу.

## Роли в базе

Три роли и ни одной лишней. Разделение — не бюрократия, на нём держится §13.

| Роль | Кто такая | Атрибуты |
|---|---|---|
| `app_tenant` | под ней идут все запросы экранов | `NOLOGIN`, не superuser, не владелец таблиц |
| `carswap_owner` | владелец схемы, под ним едут миграции | `LOGIN`, не superuser |
| `carswap_app` | роль подключения приложения, входит в `app_tenant` | `LOGIN`, своих прав не имеет |

`app_tenant` намеренно не superuser и не владелец таблиц. RLS с `force`
применяется и к владельцу, но superuser её обходит целиком — и тогда
изоляция точек перестаёт проверяться на живом пути. Не громко, а молча:
экраны продолжат работать, просто точка увидит чужих клиентов. Подключение
приложения под `postgres` — единственный способ незаметно отключить всю
защиту §13 разом.

Владелец должен быть **один и тот же для всех миграций**: `005_grants.sql`
выполняет `alter default privileges`, а они действуют от имени того, кто их
выполнил. Сменившийся владелец молча оставит таблицы будущих миграций
без прав арендатора — и экраны упадут с «permission denied» через месяц.

**На управляемом Postgres**, куда init-скрипт не положить, роли заводятся
руками до первого наката. Либо, если это невозможно, `carswap_owner`
выдаётся `CREATEROLE` — тогда `005_grants.sql` заведёт `app_tenant` сам.
Без того и другого накат остановится на пятой миграции с
`permission denied to create role`.

## Разворачивание с нуля

### 1 · Сервер

Selectel, облачный сервер в зоне РФ. Минимум для одной сети точек:
2 vCPU, 4 ГБ памяти, 40 ГБ системного диска и **отдельный диск под данные** —
Postgres и хранилище фото не должны делить файловую систему с системой.

```bash
# Ubuntu 24.04 LTS
apt update && apt install -y docker.io docker-compose-v2 git
systemctl enable --now docker

# Брандмауэр: наружу только SSH и веб. База и приложение портов не
# публикуют вовсе — они видны друг другу по внутренней сети compose.
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp && ufw --force enable
```

Отдельный диск под данные Docker:

```bash
mkfs.ext4 /dev/vdb
mkdir -p /var/lib/docker-data && mount /dev/vdb /var/lib/docker-data
echo '/dev/vdb /var/lib/docker-data ext4 defaults 0 2' >> /etc/fstab
# и переезд каталога docker на него — либо через data-root в daemon.json
```

### 2 · Код

```bash
mkdir -p /srv && cd /srv
git clone <репозиторий> carswap && cd carswap/deploy
```

Образ приложения и каталог `app/db` **обязаны быть из одного коммита**.
Иначе код читает не ту схему, которая накачена, и ловится это уже на живой
точке. Разворачивайте только по тегу или хэшу, не по «последнему в ветке».

### 3 · Параметры

```bash
cp .env.example .env
chmod 600 .env

# Три РАЗНЫХ пароля, генерировать, а не придумывать:
openssl rand -base64 32 | tr -d '/+=' | cut -c1-32
```

Заполнить `POSTGRES_SUPERUSER_PASSWORD`, `CARSWAP_OWNER_PASSWORD`,
`CARSWAP_APP_PASSWORD` и `APP_TAG=$(git rev-parse --short HEAD)`.

Ключи каналов (`WAZZUP_*`) можно оставить пустыми: без них не работает
отправка карточек, но контур поднимается и экраны открываются.

### 4 · База

```bash
docker compose up -d db
docker compose logs -f db      # ждём «database system is ready»
```

Скрипт `postgres/initdb/00-roles-and-extensions.sh` отработает **ровно
один раз**, при пустом каталоге данных: заведёт три роли, поставит
`pgcrypto` и `pg_trgm`, передаст схему `public` владельцу. В логе должна
быть строка «роли app_tenant / carswap_owner / carswap_app и расширения
созданы». Повторный `up` сюда уже не заходит.

Файл должен быть исполняемым (`chmod +x`) — git это хранит, но при
копировании архивом бит теряется, и скрипт молча не отработает.

### 5 · Миграции

```bash
docker compose --profile tools run --rm migrate
```

Накатывает миграции из `app/db/migrations/*.sql` по возрастанию имени.
Идемпотентно: учёт ведётся в `deploy.schema_migrations`, повторный запуск
ничего не делает. Вместе с записью хранится sha256 файла — правка уже
применённой миграции остановит следующий накат, вместо того чтобы дать
базе и репозиторию разойтись незаметно.

```bash
docker compose --profile tools run --rm migrate --status    # что применено
docker compose --profile tools run --rm migrate --dry-run   # что будет накачено
```

### 6 · Посев

```bash
docker compose --profile tools run --rm seed
```

Посев идёт **под суперпользователем**, и это единственное место, где так
можно. Причина: `seed.sql` пишет в таблицы с `force row level security`,
а `force` действует и на владельца схемы — под `carswap_owner` посев падает
на первой же вставке в `points`. Обходит RLS только superuser. Допустимо
потому, что посев выполняется один раз при установке и не является частью
живого пути.

`seed.sql` — данные для разработки и демонстрации: вымышленные сети, точки,
клиенты и телефоны. На боевом контуре, где будут настоящие ПД, посев либо
не запускается вовсе, либо запускается один раз на пустой базе до
подключения первой точки.

### 7 · Приложение и прокси

```bash
docker compose build app
docker compose up -d app proxy
```

### 8 · TLS

```bash
docker run --rm -v carswap_certs:/etc/letsencrypt -v carswap_acme:/var/www/acme \
  certbot/certbot certonly --webroot -w /var/www/acme \
  -d carswap.example.ru --agree-tos -m почта@example.ru --no-eff-email
```

Затем в `nginx/carswap.conf` раскомментировать блок 443, подставить домен,
а блок 80 превратить в редирект (оставив на HTTP `/healthz` и
`/.well-known/acme-challenge/`), и `docker compose restart proxy`.
Продление — задание в cron с `certbot renew` и перезапуском прокси.

### 9 · Проверка

```bash
# контейнеры живы и здоровы
docker compose ps

# прокси отвечает о себе
curl -s http://localhost/healthz

# заголовки на месте: CSP без внешних источников
curl -sD- -o /dev/null http://localhost/ | grep -i content-security

# журнал миграций полон
docker compose --profile tools run --rm migrate --status

# роли такие, как задумано: ни одной с superuser или bypassrls
docker compose exec -T db psql -U postgres -d carswap -tAc \
  "select rolname, rolsuper, rolbypassrls from pg_roles
    where rolname in ('app_tenant','carswap_app','carswap_owner')"

# изоляция точек работает на живом пути, а не только в тестах:
# один и тот же запрос под разными претензиями должен давать разные ответы
docker compose exec -T db psql -U carswap_app -d carswap -tAc \
  "begin;
   select set_config('request.jwt.claims','{\"point_id\":\"<uuid точки>\",\"app_role\":\"manager\"}',true);
   set local role app_tenant;
   select count(*) from clients;
   commit;"

# инварианты схемы — на ОТДЕЛЬНОЙ чистой базе, не на боевой:
# tests/*.sql заводят свои фикстуры и конфликтуют и с посевом,
# и тем более с данными живой точки.
docker compose exec -T db psql -U postgres -d postgres \
  -c "create database carswap_check owner carswap_owner"
docker compose --profile tools run --rm \
  -e DATABASE_URL=postgresql://carswap_owner@db:5432/carswap_check migrate
docker compose --profile tools run --rm --entrypoint psql seed \
  "postgresql://postgres@db:5432/carswap_check" -X \
  -f /db/tests/invariants.sql | grep -c 'ok  ·'
docker compose exec -T db psql -U postgres -d postgres -c "drop database carswap_check"
```

Про остальные три файла тестов (`queue.sql`, `consent-rolls.sql`,
`operations.sql`) читайте следующий раздел: на боевой ролевой модели они
проходят не полностью, и это ожидаемо.

### Почему `db/test.sh` не проверяет боевую ролевую модель

`app/db/test.sh` поднимает временный кластер и делает всё под `postgres`.
Значит, таблицы и девять функций `security definer` в схеме `app`
принадлежат суперпользователю — и RLS для них не существует вовсе.

На сервере владелец другой: `carswap_owner`, не superuser. Функции
`security definer` выполняются от его имени, а `force row level security`
действует и на владельца. Поведение получается разное, и разница
не теоретическая — проверено:

| | `test.sh` (владелец `postgres`) | сервер (владелец `carswap_owner`) |
|---|---|---|
| `app.enqueue_render` без претензий | ставит задачу | `ERROR: new row violates row-level security policy` |
| `app.enqueue_render` с претензиями точки | ставит задачу | ставит задачу |
| `tests/invariants.sql` | 18 зелёных | 18 зелёных |
| `tests/queue.sql` | зелёные | падает на первой же вставке |
| `tests/consent-rolls.sql` | зелёные | падает на первой же вставке |
| `tests/operations.sql` | зелёные | падает на первой же вставке |
| всего | 49 зелёных | 18 зелёных из 49 |

Падают они не потому, что схема сломана, а потому что фикстуры вставляются
без претензий точки: под суперпользователем это проходит, под владельцем —
нет. Тридцать одна проверка из сорока девяти на боевой конфигурации просто
не выполняется.

**Живой путь продукта от этого не страдает** — `withTenant()` выставляет
претензии перед каждым запросом, и `enqueue_render` под ними отрабатывает.
Проверено на этом же контуре.

Страдают два места:

1. **Тесты не сторожат боевую конфигурацию.** Регрессия, которая ломается
   только при владельце-не-суперпользователе, зелёным `test.sh` не ловится.
2. **Фоновым заданиям претензий взять неоткуда.** `claim_render_jobs`
   и `requeue_stale_jobs` написаны для воркера очереди, который работает
   не от имени точки. Под боевой ролевой моделью он упрётся в ту же RLS.
   Решать это надо до запуска воркера — и решать осознанно, а не выдачей
   роли воркера `BYPASSRLS`, потому что это отменяет §13 целиком.

Экраны: `/login`, `/inbox`, `/g/<slug точки>`, `/bay`, `/owner`, `/crm`.
Полный список из 32 маршрутов — в `app/qa.sh`.

## Обновление

```bash
cd /srv/carswap && git fetch && git checkout <тег>
cd deploy
export APP_TAG=$(git rev-parse --short HEAD)
docker compose build app
docker compose --profile tools run --rm migrate   # ДО подъёма нового кода
docker compose up -d app
```

Порядок именно такой: миграции накатываются до того, как поднимется код,
который на них рассчитывает. Обратное даёт окно, в котором экраны бьются
в несуществующие столбцы.

Откат кода — `APP_TAG` предыдущей сборки и `docker compose up -d app`.
Откат схемы автоматическим не бывает: обратных миграций в проекте нет
намеренно, потому что подтверждения и конфигурации иммутабельны, и «откат»
структуры на живых данных — это потеря данных. Если схема поехала не туда,
чините вперёд новой миграцией.

## Резервные копии

```bash
./backup.sh                      # снять копию
./backup.sh --check <файл.dump>  # проверить читаемость снятой
```

В cron:

```
0 3 * * * cd /srv/carswap/deploy && ./backup.sh >> /var/log/carswap-backup.log 2>&1
```

### Что копируется и почему обе половины обязательны

**Данные Postgres.** Подтверждения клиентов, конфигурации примерок, наряды,
согласия на обработку ПД, аудит-лог, справочники и прайсы точек.

**Том с хранилищем фото** (`carswap_storage`). Исходные снимки машин и
рендеры, на которые ссылаются `storage_path` в базе.

Копия только базы бесполезна: карточка без картинок не показывает, что
именно клиент подтвердил. Копия только хранилища бесполезна тоже: файл без
записи в базе — просто jpg без владельца, точки и срока хранения. Поэтому
`backup.sh` снимает обе одним запуском и под одной меткой времени.

### Почему потеря подтверждённых выборов клиентов недопустима

На них держится защита от переклейки — самая дорогая поломка в продукте.

Мастер берёт рулон другой партии или похожий артикул, машина оклеена не той
плёнкой, дальше цикл переклейки: 50–150 тысяч рублей и неделя занятого
поста. Дороже, чем год подписки точки.

Защита устроена так (`003_consent_rolls_audit.sql`, `app.enforce_roll_match`):
наряд **не переводится в работу**, пока артикул отсканированного рулона
не сошёлся с артикулом подтверждённой клиентом конфигурации. Проверка стоит
в триггере базы, а не на экране сканера, — на экране её можно обойти,
в базе нельзя.

Всё это работает ровно до тех пор, пока запись подтверждения существует.
Потеряли `confirmations` и `configuration_items` — и:

- нечему сверять рулон, защита от переклейки просто перестаёт существовать;
- в споре с клиентом нечем показать, что именно он подтвердил, и на чьей
  стороне ошибка;
- согласия на обработку ПД тоже в базе, а `photos` без `consent_id`
  вставить нельзя — восстановление фото без записей о согласии
  превращает архив в нарушение.

Подтверждения и конфигурации в схеме **иммутабельны**: их нельзя
переписать, только создать новое. Это значит, что у потерянной записи нет
и не может быть «свежей версии» где-то ещё. Восстановить её неоткуда,
кроме резервной копии.

### Куда складывать

Копия, лежащая на том же сервере, защищает от ошибки оператора и порчи
таблицы, но не от потери сервера. Уносите на отдельный ресурс — и **только
в РФ**: в копии те же персональные данные, что в базе, и требование
ст. 18 ч. 5 152-ФЗ распространяется на копии тоже. Объектное хранилище
Selectel в российской зоне подходит, S3 у зарубежного провайдера — нет.

Копии содержат ПД: каталог с ними — `chmod 700`, файлы — `600`,
`backup.sh` выставляет это сам. Внутрь репозитория складывать нельзя,
скрипт на это ругается и отказывается работать.

### Восстановление

```bash
# 1. Остановить приложение, чтобы никто не писал в базу во время работ
docker compose stop app

# 2. Чистая база и накат дампа
docker compose exec -T db psql -U postgres -d postgres \
  -c "create database carswap_restore owner carswap_owner"
docker cp db-20260829-041115.dump carswap-db-1:/tmp/r.dump
docker compose exec -T db pg_restore -U postgres -d carswap_restore /tmp/r.dump

# 3. Убедиться, что вернулось главное
docker compose exec -T db psql -U postgres -d carswap_restore -tAc \
  "select 'подтверждений: '||(select count(*) from confirmations)
       ||', таблиц с force RLS: '||(select count(*) from pg_class where relforcerowsecurity)"

# 4. Хранилище фото
docker run --rm -v carswap_storage:/storage -v /var/backups/carswap:/b:ro \
  alpine:3.20 tar -C /storage -xzf /b/storage-20260829-041115.tar.gz

# 5. Переключить приложение на восстановленную базу. Соединений к старой
#    быть не должно — приложение остановлено на первом шаге.
docker compose exec -T db psql -U postgres -d postgres \
  -c "alter database carswap rename to carswap_broken" \
  -c "alter database carswap_restore rename to carswap"
docker compose start app

# 6. Старую базу удалять не раньше, чем убедитесь, что точка работает.
#    Потом: drop database carswap_broken
```

Дамп снимается без `--no-owner` и без `--no-privileges` намеренно: роли,
гранты и политики RLS — часть защиты, и копия обязана уметь восстановить их
вместе с данными. Проверено: после восстановления возвращаются и данные,
и 39 таблиц с `force row level security`, и гранты `app_tenant`.

Проверять восстановление надо не в тот день, когда оно понадобится.
Раз в квартал — накат последней копии в отдельную базу и сверка счётчиков.

## Хранение персональных данных

Схема задаёт срок хранения при записи, а не «когда-нибудь настроим»:
у `photos` есть `retain_until` со значением по умолчанию `now() + 12 месяцев`
и индекс `photos_retention` по нему, у `clients` — такой же `retain_until`
(миграция `007_retention.sql`). Исполняет эти сроки сервис `retention` —
см. следующий раздел.

Логи прокси пишутся без тела запроса и без query-строки (`log_format
carswap` в `nginx/carswap.conf`): туда попали бы ПД, а логи прокси
не входят в контур, для которого объявлен режим обработки.
`log_min_duration_statement=1000` у Postgres пишет только медленные
запросы — текст SQL без значений параметров.

## Уничтожение персональных данных по сроку

152-ФЗ ст. 5 ч. 7 и ст. 21: по достижении цели обработки или по истечении
объявленного срока данные обязаны быть уничтожены, и уничтожение обязано
быть подтверждаемым. Объявленный, но не исполняемый срок хуже отсутствующего:
он превращает политику обработки в обещание, которого система не держит.

Механизм разложен на две половины, и это не случайность, а следствие того,
что строка живёт в Postgres, а файл — в томе `carswap_storage`, и общей
транзакции у них нет.

| Что | Где |
|---|---|
| поиск просроченного, стирание строк, запись в журнал | `app.expire_personal_data(batch)` в `app/db/migrations/007_retention.sql` |
| очередь путей файлов на физическое удаление | таблица `file_erasures` |
| удаление файлов с диска и закрытие пометок | `deploy/retention.sh`, сервис `retention` |

### Порядок и что происходит при обрыве

`пометить → удалить файл → закрыть пометку`.

Первый шаг — одна транзакция базы: строка с ПД стирается или обезличивается,
путь файла ложится в `file_erasures`, в `audit_log` появляется запись.
Второй шаг забирает пометки и удаляет файлы.

Обрыв между шагами оставляет состояние «строки ПД уже нет, файл ещё лежит,
пометка жива» — следующий запуск доделает. Обратный порядок оставил бы файл
удалённым, а запись в базе — ссылающейся в пустоту: тихая порча, которую
никто не найдёт. Пропавший файл (`ENOENT`) считается успехом: цель в том,
чтобы файла не было, а не в том, чтобы удалили именно мы.

### Что удаляется, а что обезличивается

Удалить всё, что связано с клиентом, нельзя: закрытый наряд на 150 тыс. ₽
с выданной гарантией — это бухгалтерия и обязательство перед клиентом,
а не персональные данные. Поэтому обезличивание идёт **по субъекту**:
снимаются идентификаторы, учётный скелет остаётся.

- **удаляются целиком** — просроченные `photos`, на которые не ссылается
  примерка, их `photo_masks`, переписка (`messages`), фото ЛКП
  (`condition_photos`), уведомления;
- **обезличиваются** — `clients` (имя, телефон, госномер; марка и модель
  остаются: это характеристика автомобиля, а не человека) и те `photos`,
  на которых стоит подтверждённая примерка;
- **не трогаются** — `orders`, `invoices`, `warranties`, `confirmations`,
  `configurations`. Они иммутабельны и на них держится учёт.

Клиент обезличивается только когда цель обработки действительно достигнута:
вышел `retain_until`, **и** истекла гарантия, **и** закрыты наряды, **и** нет
непросроченных фото, **и** нет переписки свежее объявленного срока. Каждое
условие — отдельное основание хранить дальше по ст. 5 ч. 7.

### Запуск

Сервис `retention` поднимается вместе со стеком (`docker compose up -d`)
и сам выдерживает интервал. Cron внутри контейнера приложения намеренно не
заводился: приложение масштабируется горизонтально, и cron в нём означал бы
N параллельных проходов на N копиях плюс тихую смерть задания при каждом
обновлении образа. Cron на хосте потребовал бы ручной строчки в crontab
на каждом сервере — обязанность по закону не должна от этого зависеть.

```bash
# что делает постоянный сервис
docker compose logs -f retention

# один проход руками
docker compose run --rm retention --once

# показать, что удалил бы, ничего не удаляя
docker compose run --rm retention --dry-run

# сколько просрочено прямо сейчас
docker compose exec -T db psql -U carswap_app -d carswap -tAc \
  "select * from app.retention_status()"

# доказательство для проверяющего: что уничтожено, когда и на каком основании
docker compose exec -T db psql -U carswap_app -d carswap -tAc \
  "begin;
   select set_config('request.jwt.claims','{\"point_id\":\"<uuid точки>\",\"app_role\":\"owner\"}',true);
   select at, entity, detail->>'basis', detail
     from audit_log where action = 'erase' order by at desc limit 20;
   commit;"
```

Настройки — `RETENTION_INTERVAL` (секунды между проходами, по умолчанию
3600) и `RETENTION_BATCH` (размер порции, по умолчанию 500). Порции нужны,
чтобы не держать долгую транзакцию на живой базе; проход повторяется,
пока не перестанет находить работу.

### Чего этот механизм НЕ удаляет

Честный список остатков — их надо знать до разговора с проверяющим.

1. **`renders`** — сгенерированные изображения машины клиента. Триггер
   `app.renders_qa_only` (миграция 001) запрещает и удаление рендера, и
   правку пути: рендер — доказательство того, что именно клиент подтвердил,
   в споре ценой 50–150 тыс. ₽. Файлы рендеров переживают уничтожение ПД.
2. **`ip` и `user_agent` в `consents` и `confirmations`** — эти таблицы
   закрыты триггером `app.forbid_mutation`. Само подтверждение удалить
   нельзя и по другой причине: на нём висит `orders.confirmation_id NOT NULL`,
   то есть учёт. После снятия идентификаторов субъекта эти следы ни с кем
   не сопоставляются, но физически остаются.
3. **Файлы в хранилищах мессенджеров.** Вложение с `contentUri` шлюза лежит
   не в нашем томе. Пометка закрывается с пояснением «путь вне тома
   хранилища», и это видно в `file_erasures.last_error`.

Пункты 1 и 2 лечатся отдельной миграцией, снимающей иммутабельность при
достигнутой учётной цели. Здесь этого нет намеренно: ослабление инварианта
О-4 — отдельное решение с отдельным обоснованием, а не побочный эффект
задания на удаление.

## Что осталось сделать руками

Честный список. Ничего из этого нельзя закрыть из репозитория.

1. **Сервер, диски, DNS, сертификат** — заказ и первичная настройка
   в панели Selectel и у регистратора.
2. **Пароли** — сгенерировать и положить в `deploy/.env`. В репозитории
   их нет и не будет.
3. **Ключи каналов** — получить в кабинете Wazzup, прописать
   `WAZZUP_API_KEY` и `WAZZUP_CRM_KEY`, зарегистрировать адрес вебхука.
4. **Вывоз копий за пределы сервера** — `backup.sh` кладёт их локально;
   отправка в объектное хранилище Selectel и проверка, что она идёт,
   настраиваются отдельно.
5. **Проверка, что уничтожение ПД действительно идёт.** Сервис `retention`
   поднимается сам, но никто не заметит, если он встанет: мониторинга в
   контуре нет. До подключения первой реальной точки — глазами раз в
   неделю: `docker compose logs --tail 50 retention` и
   `select * from app.retention_status()`.
6. **Мониторинг** — ни метрик, ни оповещений в контуре нет. Сейчас о том,
   что контур лёг, узнают от точки.
7. **`sys()` и роль приложения** — см. ниже, это требует правки кода.

### Про `sys()`

`app/src/lib/db.ts` содержит две двери в базу: `withTenant()` — под ролью
арендатора с претензиями точки, и `sys()` — «запросы вне арендатора».
В разработке приложение подключается суперпользователем, и `sys()` пишет
куда угодно, обходя RLS. На боевой ролевой модели `carswap_app` под RLS
попадает тоже, а претензий в этой сессии нет — и запись **молча не
происходит**: `update` возвращает 0 строк, исключения нет.

Проверено на временном кластере: одна и та же запись даёт `UPDATE 1` под
`postgres` и `UPDATE 0` под `carswap_app`. Сейчас через `sys()` идут
платежи и перенос записей в `src/lib/journey.ts`.

Чинится в коде, не в деплое: перенести эти вызовы в `withTenant()`.
Выдать роли приложения `BYPASSRLS` было бы способом «починить» это за
пять минут и одновременно отменить всё, ради чего RLS ставили.

## Известные ограничения контура

- **Хранилище фото — том на том же сервере.** Отдельного объектного
  хранилища нет. При росте это первое, что упрётся.
- **Один сервер.** Ни репликации Postgres, ни второй копии приложения.
  Обновление приложения — короткий перерыв.
- **Запись файлов в хранилище приложением ещё не реализована.** Рендеры
  сейчас ссылаются на демонстрационные файлы из `public/renders`,
  запечённые в образ. Том `carswap_storage` и отдача `/storage/` прокси
  подготовлены заранее, но живого кода, который туда пишет, пока нет.
  Следствие для уничтожения ПД: пути вида `/renders/...` лежат не в томе,
  а в образе, и `retention.sh` закрывает такие пометки с пояснением
  «путь вне тома хранилища». Как только приложение начнёт писать в
  `/storage/`, они начнут удаляться физически — механизм этого уже ждёт.
- **`clients.retain_until` не двигается при новом обращении.** Срок
  выставляется при заведении клиента, а приложение его не продлевает.
  Чтобы активного клиента не обезличило посреди работы с ним,
  `app.client_retention_due` дополнительно требует отсутствия свежей
  переписки, живой гарантии и открытых нарядов. Это заплатка в базе на
  месте отсутствующей логики в коде, и правильное место для починки —
  код приложения.
