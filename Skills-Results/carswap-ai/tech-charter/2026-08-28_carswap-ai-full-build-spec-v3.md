# §1. Что строим

Рабочее место точки детейлинга и публичная примерочная. Два ядра, оба в основной области, оба строятся сразу.

**Ядро 1 — инбокс и диалог.** Обращения из WhatsApp, Telegram, MAX, Авито, VK, Instagram приходят в один список в кабинете точки. Менеджер открывает диалог, собирает примерку в панели внутри него и отправляет одним действием. Ответ уходит обратно в тот канал, откуда пришло обращение. За ≤3 минуты клиент получает карточку: рендер именно его машины, артикул из прайса именно этой точки, цена этой точки, неотключаемая строка про сверку оттенка на замере.

**Ядро 2 — гараж-примерочная.** Публичная страница по ссылке точки или сети. Клиент грузит фото своей машины или выбирает марку и модель, примеряет плёнку, диски, обшивку салона, обвес, комбинирует, сравнивает варианты рядом, делится ссылкой. Выбранная конфигурация уходит в чат точки с артикулами и ценой.

**Обслуживающий слой:** карточка клиента с историей примерок, статусы и воронка, прайс точки, заказ-наряд и счёт из подтверждённой конфигурации, экран мастера у поста, недельная сводка владельцу, кабинет сети.

**Плательщики:** владелец точки, сеть-франшиза (биллинг за точку), премиальный автосалон (программа с white label).

# §2. Инварианты. Инженерному пересмотру не подлежат

Нарушение любого из них означает, что продукт перестал решать Работу, ради которой строится.

1. **Ноль переходов в другой контекст между обращением и отправкой.** Менеджер не выходит из диалога. Всё, что требует переключения приложения или вкладки, — брак.
2. **Артикул и цена берутся только из прайса этой точки.** Отправить примерку без артикула и цены технически невозможно. Ручной ввод — ноль символов.
3. **Механика честности по цвету неотключаема.** Строка про сверку оттенка партии на замере уходит с каждой карточкой. Тумблера нет ни у менеджера, ни у владельца, ни у сети.
4. **Машина клиента должна остаться узнаваемой.** Номер, геометрия кузова, фон, диски вне зоны изменения — те же пиксели, что на исходном фото. Не «похожие», а те же. См. §4.
5. **Фото не является гейтом.** Первая примерка доступна по марке и модели, без фото и без регистрации.
6. **Мы не визуализируем качество чужого труда.** Полировка, керамика, химчистка, PDR, реставрация — не показываются никогда. См. §4.2.
7. **Модель генерации — сменная деталь.** Ни один слой продукта не знает имени вендора. Смена модели — замена адаптера, не переписывание.
8. **Мультиарендность с первого дня.** Точка, сеть, изоляция данных, брендирование — в схеме, а не в надстройке.
9. **Стоимость генерации — метрика в проде.** Расход считается на точку, на сессию, на пользователя, в реальном времени, с жёсткими потолками.
10. **Повторяемость важнее красоты.** Экран мастера обязан показать ровно ту картинку, которую подтвердил клиент. Всё, что не воспроизводится побитово, не может быть доказательством.

## 3.2 Стек и почему

## 3.3 Критическая поправка по модели

**`gemini-3.1-flash-image` — это генератор. `Gemini 3.1 Pro` — нет.** Gemini 3.1 Pro принимает изображения на вход и отдаёт только текст; для сборки промпта его использовать можно, для генерации нельзя.

**Линейка Imagen выключена 17.08.2026.** Вместе с ней у Google исчез единственный API с явной бинарной маской. Маску теперь можно задать только словами — а значит, локальность изменения обеспечиваем мы, а не модель. Это и есть причина архитектуры §4.

# §4. Пайплайн рендера

## 4.1 Несущий принцип

**Модель перерисовывает кадр целиком.** Она не «меняет колёса» — она генерирует новое изображение по мотивам старого. Номер, фон, геометрия кузова не сохраняются ни промптом, ни просьбой.

Отсюда единственная работающая схема:

```
оригинал ──► сегментация ──► маска области
   │                              │
   │         ┌────────────────────┴─────────────┐
   │         │                                  │
   │    детерминированная                  генеративная
   │    операция в маске                   правка в маске
   │         │                                  │
   │         └────────────────┬─────────────────┘
   │                          │
   └──────────► КОМПОЗИТИНГ ОБРАТНО НА ОРИГИНАЛ ◄──┘
                              │
                    оверлей: артикул, цена,
                    строка честности, бренд точки
                              │
                          QA-гейт
                              │
                          доставка
```

**Что мы получаем бесплатно:** всё вне маски — оригинальные пиксели по построению. Номер читается, фон тот же, кузовные линии не поплыли. Инвариант №4 выполняется арифметикой, а не доверием к модели.

**Второе следствие, не менее важное:** детерминированные операции **повторяемы**. Тот же вход и те же параметры дают тот же выход всегда. Генерация каждый раз даёт другое. Экран мастера (§8) обязан показать ровно то, что подтвердил клиент, — значит, всё, что можно сделать формулой, делается формулой.

## 4.2 Матрица категорий

Четыре класса. Класс определяет маршрут в пайплайне.

### Класс A — детерминированные. Модель не вызывается.

| Категория | Что физически меняется | Операция |
|---|---|---|
| **Тонировка стёкол** | пропускание света | Разделение отражения и пропускания по светлоте, умножение пропускания на VLT в линейном свете |
| **Окрас дисков и суппортов** | собственный цвет металла | Подмена цветности при сохранении светлоты (LAB) |
| **Смена цвета кузова, глянец → глянец** | собственный цвет ЛКП/плёнки | То же, маска кузова с исключениями |
| **Звёздное небо** | добавляется источник света | Процедурная генерация точек со свечением, аддитивное наложение |
| **Три световых условия** | экспозиция и баланс белого | Сдвиг по одному рендеру. **Не три генерации** |

### Класс B — гибридные. Маска детерминированная, содержимое генеративное.

| Категория | Почему нужна модель |
|---|---|
| **Смена финиша: глянец → мат / сатин / хром** | Меняется материал, а не цвет. Мат гасит отражения, подменой цветности это не делается |
| **Смена цвета из тёмного в светлое** | В тёмном исходнике завалены тени, доставать нечего |
| **Замена дисков на другую модель** | Меняется геометрия внутри маски |
| **Антихром** | Смена материала: зеркало → сатин. Нужна тон-компрессия плюс синтез мягкого блика по кромке |
| **Перешив салона, перешив руля** | Меняется материал, фактура, строчка |
| **Карбон в салоне** | Появляется текстура с направлением плетения |

### Класс C — не в MVP.

| Категория | Причина |
|---|---|
| **Обвес** | Меняется силуэт — прямое нарушение инварианта №4. Ни один конкурент в мире не решил под конкретный каталожный комплект. Возможен только как помеченный «концепт» |
| **Выдвижные пороги** | Мелкая механика, почти всегда неудачный ракурс, два состояния |
| **Мультимедиа, мониторы** | Добавление геометрии в сложной сцене салона |

### Класс D — запрещено к визуализации. Инвариант №6.

Полировка любая · керамическое покрытие · химчистка салона · антидождь · шумоизоляция · PDR · покраска · реставрация кожи · восстановление оптики.

**Причина не техническая, а продуктовая.** Результат этих работ — обещание качества чужого труда. Сгенерировав «после полировки», мы своими руками создаём спор на выдаче — тот самый, против которого построен экран мастера. Продукт показывает **выбор**, а не результат работы.

Реализация запрета: список категорий класса D в конфиге, отсутствие роутов, отсутствие в каталоге. Не «спрятано в UI», а недоступно на уровне API.

## 4.3 Сегментация

**Стадия 1 — гейт качества исходника.** До всякой обработки: есть ли на кадре автомобиль, какой ракурс, достаточно ли разрешения, нет ли смаза. Плохой исходник отклоняется с внятной причиной **до** списания денег на генерацию.

**Стадия 2 — маски.** SAM 3 по концепту. Набор масок на фото:

`body` · `glass_front` · `glass_side` · `glass_rear` · `wheel_fl/fr/rl/rr` · `caliper_*` · `tire_*` · `headlight` · `taillight` · `chrome_trim` · `grille` · `badge` · `mirror` · `door_handle` · `plate` · `headliner` (для салона) · `seat_*` · `steering_wheel` · `dashboard`

**Маски считаются один раз на фото и кэшируются.** Все последующие категории на этом же фото переиспользуют их. Это главная экономия по времени и по деньгам.

**Маска `plate` — особая.** Номер всегда исключается из зоны любых изменений и всегда возвращается из оригинала. Это и инвариант №4, и снятие юридического риска.

**Растушёвка краёв обязательна.** Жёсткая граница маски выдаёт монтаж мгновенно. Ширина растушёвки — функция разрешения, не константа.

## 4.4 Детерминированные операции — как считать

### Тонировка

Физика: плёнка гасит **проходящий** свет, но почти не гасит **отражение** на поверхности стекла. Поэтому наивное затемнение всей области серым даёт узнаваемо фальшивый вид.

```
1. Перевести область стекла в линейный свет (снять гамму sRGB)
2. Разделить на компоненты по светлоте с мягким порогом:
   - светлое = отражение (небо, блики) → почти не трогаем
   - тёмное и средние = пропускание (салон) → умножаем на VLT
3. out_linear = specular + VLT × transmission
4. Вернуть гамму
```

Порог разделения — не константа, а перцентиль по гистограмме области. Порог с мягким переходом, иначе на границе появится ступенька.

**Ограничение, зашитое в продукт: только в сторону темнее.** Если стекло уже тонировано, показать светлее нельзя — информации в пикселях нет. UI обязан это знать и не предлагать невозможного: при обнаружении существующей тонировки доступны только более тёмные VLT.

Пресеты VLT: 50 · 35 · 20 · 15 · 5. Значения — численные, совпадают со строками прайса.

### Окрас дисков и суппортов

Физика: форма та же, свет тот же, меняется собственный цвет металла.

```
1. Перевести маску диска в LAB
2. L (светлота) — оставить как есть. В ней живут блики, тени и объём спиц
3. a, b (цветность) — заменить на целевые
4. Опционально: масштабировать насыщенность, сохранив локальный контраст
5. Обратно в sRGB, композитинг по маске
```

**Ограничения, которые обязан знать UI:**
- **Светлое → тёмное: отлично** (серебро → чёрный, графит, бронза). В светлом исходнике есть вся детализация.
- **Тёмное → светлое: плохо.** В чёрных дисках тени завалены. Маршрутизировать в класс B.
- **Полированный хром → мат: класс B.** Это смена материала. Подменой цветности получится «затонированный хром» с зеркальными отражениями.

Суппорт: цвет проще, маска сложнее — он мелкий и наполовину за спицами. При площади маски ниже порога — не предлагать.

### Смена цвета кузова, глянец → глянец

Та же операция, что на дисках, но маска сложнее: `body` минус `glass_*`, `headlight`, `taillight`, `tire_*`, `chrome_trim`, `badge`, `plate`, `mirror` (если другого цвета), `door_handle`.

**Это ключевая экономия.** Если оклейка глянцевым винилом из светлого исходника — генерация не нужна вообще. Проверка на входе: класс финиша исходника, класс финиша цели, направление по светлоте. Совпало — класс A, не совпало — класс B.

### Звёздное небо

Чистая процедурная графика, модель не участвует.

```
1. Маска потолка
2. Если кадр светлый — сначала привести к вечернему тону
3. Распределить N точек:
   - плотность растёт к дальнему краю по перспективе
   - рисунок: равномерный / созвездия / градиент — параметр
4. Каждая точка = яркое ядро + мягкое свечение (гауссово затухание)
5. Свечение слегка подсвечивает окружающую обшивку
6. Аддитивное наложение в линейном свете
```

Параметры численные и совпадают с прайсом: число волокон (200 / 400 / 600), наличие «падающих звёзд», цветовая температура.

### Три световых условия

**Не три генерации.** Один рендер, три вывода: дневной свет, тень, искусственное освещение. Это сдвиг экспозиции, баланса белого и контраста по кривой. Себестоимость нулевая.

## 4.5 Генеративные операции

**Вызов модели — всегда внутри маски и всегда с обратным композитингом.** Выход модели никогда не является финалом.

**Что подаём:**
- Оригинал (или кроп области с запасом)
- **Референсное фото товара** — свотч плёнки, фото диска в близком ракурсе, образец кожи. Поддерживается до 6 объектов + 5 «характеров» + 3 стилевых у Pro, до 10 объектов у Flash
- Промпт с явным «изменить только X, сохранить всё остальное»

**Цвет плёнки задаётся свотчем, а не словом.** «Sapphire Blue» в промпте и реальный 3M 1080-G347 — разные цвета. В каталог кладутся фото-свотчи, подбор по ΔE (CIEDE2000).

**Никогда не наслаивать генерации.** Деградация начинается на 5–7 шаге и проявляется артефактами **в областях, которые не редактировались**. Каждая категория считается от оригинала независимо, результаты сливаются композитингом масок. «Плёнка + диски + тонировка» — это три параллельных прохода и одна сборка, а не цепочка.

**Известные точки отказа, закладывать ретраи:**
- Модель самовольно меняет посадку и клиренс машины и освещение сцены. Практик, тестировавший на дисках, дошёл до приемлемого результата за семь промптов
- Шильдики марок деградируют. Зону `badge` возвращать из оригинала всегда
- Отражения окружения в лаке, хроме и стекле — самая частая зона палева
- Ложные срабатывания фильтров безопасности на фото с людьми и отражениями. Ретрай-логика обязательна, бюджет на отказы закладывать

## 4.6 Слой артикула и цены

**Печатать текст моделью запрещено.** Точность на алфавитно-цифровых строках 80–94% — это брак у каждого пятого клиента, причём брак с неверной ценой в коммерческом предложении.

Артикул, цена, строка честности и брендирование точки — **графический слой, накладываемый нами** поверх готового рендера. Плюсы, кроме точности: цены меняются без перегенерации, оформление A/B-тестируется, локализация бесплатна.

## 4.7 QA-гейт

Автоматическая проверка перед доставкой:

1. **Pixel-diff вне маски.** Всё, что за пределами зоны изменения, обязано совпадать с оригиналом. Расхождение выше порога — брак, ретрай.
2. **OCR номера.** Номер на выходе читается тем же распознаванием и совпадает с входом.
3. **Проверка присутствия оверлея.** Артикул, цена и строка честности физически на изображении.
4. **Площадь изменения.** Если изменённая площадь сильно расходится с площадью маски — модель вышла за границы.

**No-reference метрики качества использовать нельзя** — 19 из 21 не детектируют деградацию при итеративном редактировании. Проверяем сравнением с оригиналом, а не «красотой».

# §5. Модель данных

Postgres. Мультиарендность через RLS с первого дня. Все таблицы с данными арендатора несут `point_id`, все таблицы точки — `network_id`.

## 5.1 Арендаторы и люди

```
networks         id · name · brand (лого, цвета) · price_policy · generation_cap · created_at
points           id · network_id → networks · name · address · timezone · brand_override
                 · public_slug (для гаража) · generation_cap · status
users            id · point_id · network_id · role (manager|master|owner|network_admin)
                 · phone · name · auth_id → auth.users
```

**RLS:** менеджер видит только свою точку; владелец — свою; админ сети — все точки своей сети. Мастер — только записи своей точки, только на чтение, без логина по паролю (см. §8).

**С-1 (точка не подключится в обход сети):** `points.network_id` обязателен при `networks.exclusive = true`; самостоятельная регистрация точки в такой сети закрыта на уровне API, не UI.

## 5.2 Каталог и прайс

```
catalog_items    id · category (film|wheel|interior|trim|tint|starlight)
                 · brand · sku · name · finish (gloss|satin|matte|chrome|carbon)
                 · swatch_url · reference_urls[] · lab_color (L,a,b) · attrs jsonb
point_prices     id · point_id · catalog_item_id · price · in_stock · lead_time_days
                 · deviation_from_network numeric
network_prices   id · network_id · catalog_item_id · price · deviation_allowed_pct
```

**О-3:** примерка не собирается, если у выбранного артикула нет строки в `point_prices`. Это проверка на уровне БД (внешний ключ + NOT NULL), а не в UI.
**С-4:** отклонение цены точки от сетевой валидируется триггером против `deviation_allowed_pct`.

## 5.3 Обращения и диалоги

```
channels         id · point_id · kind (whatsapp|telegram|max|avito|vk|instagram|web)
                 · provider · external_id · credentials_ref · status
threads          id · point_id · client_id → clients · channel_id · external_thread_id
                 · status · last_message_at · assigned_to
messages         id · thread_id · direction (in|out) · channel_id · body · attachments[]
                 · external_message_id · sent_at · delivery_status
clients          id · point_id · name · phone · vehicle jsonb (make, model, year, plate)
                 · source · created_at
```

**М-10 (один тред на клиента):** склейка тредов по телефону клиента поверх разных каналов. `threads.client_id` — точка склейки.
**О-5:** канал — свойство сообщения, а не раздел интерфейса. Вкладок по каналам нет (см. §6).

## 5.4 Примерки — событийная и иммутабельная модель

```
photos           id · point_id · client_id · storage_path · width · height
                 · quality_gate jsonb · masks_ref · created_at
configurations   id · point_id · thread_id · photo_id (nullable — типовой кузов)
                 · vehicle jsonb · items jsonb[] (category, catalog_item_id, params)
                 · parent_id (для домера) · created_by · created_at
renders          id · configuration_id · variant (light_day|light_shade|light_artificial)
                 · storage_path · pipeline jsonb · cost_kopecks · model_used
                 · qa_result jsonb · created_at
confirmations    id · configuration_id · render_id · client_confirmed_at
                 · honesty_shown boolean · confirmed_via (link|chat) · ip · user_agent
```

**Конфигурация иммутабельна.** Изменение = новая запись с `parent_id`. Причина: подтверждение клиента ссылается на конкретную версию, и она обязана быть неизменной навсегда. Это несущее требование экрана мастера (§8) и защиты от переклейки.

**`renders.pipeline`** хранит полный рецепт: маски, операции, параметры, версии. Этого достаточно, чтобы **воспроизвести рендер побитово** через год. Для класса A — гарантированно, для класса B — сохраняется и сам файл.

**`confirmations.honesty_shown`** — обязательное поле. Подтверждение без показанной строки честности невалидно (О-2).

## 5.5 Учётный слой

```
orders           id · point_id · configuration_id → confirmations · number · status
                 · total · created_at
invoices         id · order_id · number · amount · status · pdf_path
deals            id · point_id · client_id · configuration_id (nullable)
                 · amount · closed_at · attribution (configurator|other)
generation_usage id · point_id · user_id · session_id · cost_kopecks · category
                 · model_used · created_at
```

**В-3 (поимённые сделки с атрибуцией):** `deals.attribution = 'configurator'` проставляется, если сделка связана с подтверждённой конфигурацией.
**В-5, С-5:** `generation_usage` — источник и сводки владельцу, и потолков.

# §6. Ядро 1 — инбокс и диалог

## 6.1 Что строим

**Один список входящих.** Не вкладки по каналам. Канал — иконка на сообщении. Менеджер отвечает в диалоге, система знает, куда доставить (О-5, §1.4 PRD).

**М-1:** обращение приходит в инбокс **без единого действия менеджера**. Требование «переслать боту» отменено в версии 2 и не подлежит возврату.

**О-8, М-3:** примерка собирается в панели **внутри диалога**. Ноль переходов. От входящего фото до отправки клиенту — не более трёх действий.

**М-5:** по приходу фото автоматически стартует предгенерация трёх бестселлеров точки. К моменту, когда менеджер открыл диалог, варианты уже есть.

**М-6:** домер вариантов в том же треде создаёт `configuration` с `parent_id`, а не новую примерку.

**М-7:** выбор клиента фиксируется как `confirmation` с меткой времени, а не как реплика в чате.

**М-8:** дата замера назначается из треда.

## 6.2 Адаптер каналов

**Абстракция, а не интеграция.** Ни один слой продукта не знает имени провайдера.

```
interface ChannelAdapter {
  receive(webhook): NormalizedMessage      // входящее → единый формат
  send(threadId, content): DeliveryResult   // текст + вложения
  capabilities(): { text, images, files, initiate }
}
```

Провайдеры на старте: Wazzup, Radist, i2crm, Chat2Desk. Выбор — по цене и по покрытию каналов конкретной точки, не по любви к вендору.

**О-6:** каналы подключаем мы, точка не настраивает шлюз. Это условие В-1 (запуск за час) и С-3 (ноль обращений в УК).

**О-7 (писать первым):** зависит от канала и от провайдера. `capabilities().initiate` обязан честно отвечать `false` там, где нельзя, и UI обязан это показывать, а не молчать.

**⚠️ Открытый вопрос, закрыть до релиза Авито:** отправка **изображений** в Авито подтверждена только на приём. Если отправка недоступна — сценарий деградирует до «ответ текстом + ссылка на конфигурацию», и это должно быть написано в интерфейсе честно, а не выясняться менеджером в бою.

# §7. Ядро 2 — гараж

**Г-1:** первая примерка без аккаунта. Ноль полей до момента «ага».
**Г-2:** узнаваемость — гарантируется композитингом (§4.1), а не обещанием.
**Г-3, Г-4:** четыре категории, комбинируются в одной конфигурации. Обвес — с явной пометкой «концепт» либо вне MVP (§4.2, класс C).
**Г-5:** два варианта рядом на одном экране, без перелистывания.
**Г-6:** сохранение и шеринг. Карточка с брендом точки — открытая графовая разметка обязательна, иначе ссылка в мессенджере разворачивается голым URL.
**Г-7:** отправка конфигурации в чат точки одним действием — создаёт `thread` и `configuration`, привязанные к `points.public_slug`.
**Г-8:** вход по ссылке точки или сети; брендирование берётся из `points.brand_override` либо `networks.brand`.
**Г-9:** лимиты по §4.10. Мягкий переход после третьей генерации: «продолжить с сохранением истории → телефон», не жёсткий блок.
**Г-10:** весь путь с телефона.

**Порядок ввода:** марка и модель → результат за ~20 секунд из кэша типовых кузовов (§4.8) → «а теперь пришлите своё фото». Фото — апгрейд уже пережитого момента, а не гейт до него.

# §8. Экран мастера

Самый правый момент «ага» в продукте и единственная защита от переклейки.

**МС-1:** запись поднимается **с телефона у поста за ≤30 секунд, в два тапа**. Вход по QR или короткой ссылке, **без логина по паролю** — руки грязные. Доступ — подписанная ссылка с ограниченным сроком, привязанная к точке.

**МС-2:** четыре обязательных поля, все четыре или запись невалидна:
`артикул` · `изображение` · `отметка «клиент подтвердил»` · `дата подтверждения`

**МС-3:** сверка артикула записи с артикулом на рулоне **до старта оклейки**. Расхождение блокирует перевод статуса.

**МС-4:** на выдаче мастер показывает клиенту его собственное подтверждение.

**Интерфейс:** крупный шрифт, высокий контраст, одна колонка, работает в перчатках, читается при плохом свете в боксе.

**Техническое следствие инварианта №10:** изображение, которое видит мастер, — это байт-в-байт тот файл, который подтвердил клиент. Не перегенерация, не «похожий». `renders.storage_path` неизменен.

# §9. Владелец и сеть

## Владелец точки

**В-1:** запуск ≤1 часа, ноль обучения, ноль обязательных импортов. Каналы и прайс заводим мы.
**В-2:** покрытие входящих примерками на 4-й неделе — без опроса менеджеров.
**В-3:** поимённые сделки с атрибуцией «цвет выбран по примерке».
**В-4:** **первая сводка на 7-й день**, не по итогам месяца.
**В-5:** расход генераций и его стоимость в рублях.

## Сеть

**С-1:** невозможность подключения точки мимо сети — на уровне API.
**С-2:** пилот 5–10 точек в одном срезе.
**С-3:** ноль обращений в УК. Инженерно это означает: онбординг без участия точки, поддержка идёт напрямую к нам, а не через менеджера сети. Метрика считается и показывается.
**С-4:** сетевой прайс с разрешённым коридором отклонения.
**С-5:** жёсткий стоп по генерациям для точки.

# §10. Учётный слой

**Обслуживает примерку и нигде не является точкой входа.** Как только продукт предъявляется как CRM, он попадает в набор сравнения с АвтоДилер Онлайн от 1 495 ₽/мес, где проигрывает по определению.

**У-1:** карточка клиента с историей примерок.
**У-2:** статусы и воронка по примерочным событиям, не по абстрактным стадиям.
**У-3:** прайс точки как единственный источник артикулов и цен.
**У-4:** заказ-наряд и счёт **автоматически из подтверждённой конфигурации**, а не ручным вводом.
**У-5:** персональная ссылка клиенту с брендированием точки.
**У-6:** ноль обязательных миграций для старта.

# §11. Онбординг до первой ценности

Целевое время — час, из которого участие точки ~30 минут.

| Шаг | Кто делает | Срок |
|---|---|---|
| 01 Подключение каналов | мы | ~30 мин участия точки: доступ и подтверждение |
| 02 Загрузка прайса | мы, из любого формата | в тот же день |
| 03 Первая отправка менеджером | менеджер, вместе с нами | первые сутки |
| 04 Первая сводка | автоматически | 7-й день |

**Малый момент «ага» до главного:** первая примерка делается **не на демо-машине, а на автомобиле, физически стоящем на посту этой точки**, снятом на телефон менеджера, и результат уходит в чат смены, а не клиенту. Менеджер видит на рендере скол на своём бампере. Это единственное, что снимает прогноз «будет как картинка из интернета» до того, как он рискнёт лицом перед клиентом.

# §12. Нефункциональные требования как контракт

Это не пожелания. Нарушение любого — блокер релиза.

| Что | Уровень | Как меряем |
|---|---|---|
| Типовой кузов по марке и модели | **≤20 сек, P90** | из кэша — фактически мгновенно |
| Полная карточка с фото клиента | **≤3 мин, P90** | от загрузки фото до готовой карточки |
| Первая картинка в отправке | **≤10 сек** | остальные догружаются |
| Поднятие записи мастером | **≤30 сек, ≤2 тапа** | на 4G, на среднем телефоне |
| Действий менеджера от фото до отправки | **≤3** | считается в проде |
| Выходов из диалога | **0** | архитектурный инвариант |
| Ручной ввод артикула и цены | **0 символов** | архитектурный инвариант |
| Доступность генерации | **99,0%** | с деградацией, см. ниже |
| Себестоимость на точку в месяц | **≤1 500 ₽** при 90 примерках | `generation_usage`, алерт при превышении |

**Деградация при недоступности модели — обязательный, а не желательный сценарий.** Обращения продолжают приходить, на них можно отвечать текстом. Примерка деградирует до «сейчас пришлю» с постановкой в очередь, а не до пустого экрана и не до ошибки. Класс A вообще не зависит от внешней модели — при падении вендора тонировка, окрас дисков и звёздное небо продолжают работать.

**Асинхронность обязательна.** Официальных SLA по времени генерации вендор не публикует; замеры дают от единиц до десятков секунд. Синхронный запрос из UI недопустим — очередь и прогресс.

# §13. Персональные данные и безопасность

**Фото клиента — персональные данные.** С первого дня, а не когда придёт проверка.

- Фото используется только для примерки этого клиента и хранится в карточке этого клиента этой точки
- Не публикуется, не передаётся третьим лицам, не используется для обучения
- Срок хранения — настраиваемый, по умолчанию ограниченный; удаление по запросу — сквозное, включая рендеры и кэш
- **Номерной знак** всегда возвращается из оригинала и никогда не перерисовывается. Отдельно предусмотреть опцию замазывания номера в публикуемых материалах
- Изоляция арендаторов — RLS на уровне БД. Утечка между точками невозможна структурно, а не по договорённости
- Ссылки на конфигурации и на экран мастера — подписанные, с ограниченным сроком, не угадываемые перебором
- Логи `generation_usage` не содержат содержимого фото

**Согласие на обработку** собирается в гараже до загрузки фото. Отказ — работает сценарий по марке и модели.

# §15. Критерии приёмки

Проверяется на реальных данных, не на демо.

**Пайплайн**
- [ ] На 10 реальных фото каждая категория класса A даёт результат, который не отличить от ретуши руками
- [ ] Вне маски изображение совпадает с оригиналом побитово; номер читается тем же OCR
- [ ] Один и тот же вход и параметры дают один и тот же выход (класс A) — проверяется хешем
- [ ] Артикул и цена на изображении всегда корректны — они не генерируются
- [ ] Строка честности присутствует на 100% карточек, отключить её невозможно ни одной ролью
- [ ] Категории класса D недоступны на уровне API, а не спрятаны в интерфейсе
- [ ] При недоступности вендора класс A продолжает работать

**Экономика**
- [ ] Себестоимость точки при 90 примерках ≤1 500 ₽/мес
- [ ] Потолки работают: анонимный гараж ≥3 генераций не отдаёт
- [ ] `generation_usage` сходится с реальным счётом вендора

**Продукт**
- [ ] Обращение из любого канала появляется в инбоксе без действий менеджера
- [ ] От входящего фото до отправки клиенту — не более трёх действий, ноль выходов из диалога
- [ ] Типовой кузов по марке и модели уходит за ≤20 секунд
- [ ] Первая примерка в гараже — без единого поля регистрации
- [ ] Мастер поднимает запись за ≤30 секунд в два тапа, без пароля
- [ ] Запись без любого из четырёх полей помечена невалидной
- [ ] Точка не может подключиться в обход сети при `networks.exclusive`
- [ ] Запуск точки укладывается в час, обучение — ноль занятий

**Данные**
- [ ] Менеджер одной точки не видит данные другой (проверять попыткой, а не чтением кода)
- [ ] Удаление клиента удаляет фото, рендеры и кэш сквозным образом
